# Plan First（計画優先ゲート）

出典: Superpowers (obra) の brainstorming / writing-plans / executing-plans を、
Kojiro の事業（自社SaaS/アプリ・データ分析・資料制作）向けに1本へ再構成したもの。

## 鉄則

**実装アクションの前に、必ずこのスキルを通す。** 実装アクションとは:
コードを書く／足場を作る／依存を入れる／外部プロジェクトを作る／DBスキーマを切る／
本番に触れる、など「あとで戻すのが面倒なこと」すべて。

読み取り専用の調査（既存コードを読む・リポジトリ構造を見る）はゲート前でも可。

## スキルの優先順位

複数スキルが該当するときは **プロセス（このスキル）が先**、続いて実装スキル
（`web-design` / `supabase` / `image-gen` …）、最後に効率化・検証
（`lean-code` / `codebase-graph` / `browser-automation` / `security-audit`）。

- 「X を作ろう」→ まず plan-first、承認後に実装スキル。
- 「このバグ直して」→ まず原因特定（systematic debugging 的に）→ 最小修正。

## 3つの経路（最初に分類する）

タスクの規模を見て、最初の一言で経路を宣言する。

| 経路 | 対象 | 必要な承認 |
|---|---|---|
| **Spike（探り）** | 不確実性が高く、まず試して学ぶべきもの | 「何を確かめるか＋試す方法」をユーザー承認 |
| **Bounded（限定）** | 1〜数ファイル規模、設計が自明 | チャット上の短い設計をユーザー承認 |
| **Architectural（構造）** | 新機能・新サービス・スキーマ変更・分析基盤 | 書面の仕様 → 承認 → 書面の実装計画 → 承認 |

> 事業別の目安:
> - **A 自社SaaS/アプリ**: 新機能・認証・課金・スキーマ変更は原則 Architectural。
> - **B データ分析/ML**: 新パイプライン・特徴量設計・モデル選定は Architectural。1回の集計やEDAは Bounded/Spike。
> - **C 資料・画像・契約**: 単発の生成物は Bounded、繰り返す制作フローの仕組み化は Architectural。

## 手順

### 1. 意図を掴む（Discover intent）
リクエストと文脈から「達成したい成果・誰のためか・成功の定義」を特定する。
欠けていれば、**目的や用途についての焦点を絞った質問を1つだけ** してから進む。
（アプリの種類が分かっても「なぜ作りたいか」は分からない。要件の確認はタスクの再承認依頼ではない。）

### 2. 理解を書き戻す（Write back）
「意図した成果・制約・成功基準」を短いメモにして提示し、本人が確認・修正できるようにする。
本人が言ったこと と こちらの推測 を分けて書く。修正を反映してから設計ブリーフとして扱う。

### 3. 設計を提示し承認を得る（HARD GATE）
- Spike: 確かめる問い＋試す方法 を承認。
- Bounded: チャット上の短い設計 を承認。
- Architectural: 書面の仕様をレビュー承認 → 次に書面の実装計画をレビューし、実行方法を選んでもらう。

> 返信は「提示したその段階」を承認したものとして扱う。アイデアや機能範囲への同意は、
> まだ存在しない成果物（仕様・計画）の承認ではない。承認を1つ得たからといって
> 残りの段階を飛ばさない。中断したら最も手前の未完了段階から再開する。

### 4. 実装（Executing）
承認済みの計画に沿って進める。計画から外れる判断が必要になったら、手を止めて確認。
実装中は `lean-code`（最小実装）と、必要なら `codebase-graph`（既存把握）を併用。

## レッドフラグ（これを考えたら立ち止まる）

| 思考 | 現実 |
|---|---|
| 「単純だからすぐ作れる」 | 単純な依頼ほど意図がずれる。設計を1行でも書く。 |
| 「とりあえず動くものを」 | 承認なき実装は手戻りの素。ゲートを通す。 |
| 「計画は後で書けばいい」 | 後の計画は実装を正当化するだけ。先に書く。 |
| 「承認もらった（＝全部OK）」 | 承認は提示した段階の分だけ。 |
